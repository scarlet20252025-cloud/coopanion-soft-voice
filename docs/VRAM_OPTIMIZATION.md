# 渐进 FP32 推理缓存与显存实测

作者 Asryto。本页记录 2026-10-15 的本地候选方案；尚未作为 npm 或 GitHub Release 发布。旧完整包不会因为安装新版 World 而自动获得新 DLL。

## 改了什么

原来 Talker 在加载时一次分配 1024 个位置的 FP32 K/V，共 224 MiB。桌宠通常把回复拆成短句，固定参考声源的实际输入上下文为 65 个位置，这些短句用不到整块缓存。

新 DLL 通过可选 `adaptiveKv: true` 启用渐进分配：先分配 256 个位置（56 MiB），按实际 prompt 调整；生成跨过当前容量时，以 256 个位置为一档扩展，用 GPU 内的逐层复制保留全部已用 FP32 数据。仍保留 1024 上限和原有 360 帧生成预算，不丢上下文、不提前截断、不改 Q8 权重、参考声源、采样参数或注意力精度。旧 DLL 缺少能力声明时拒绝启用，不能悄悄假装生效。

扩展前会同步 GPU，完成设备内复制，再清除引用旧存储的图并释放旧缓存。新尾部清零。两种 GPU 均运行真实原生测试：256→512→768→1024，每次检查 56 个 K/V 张量全部有效行逐值一致及尾部为零，超上限请求拒绝。

这不是无限压缩：长上下文仍需扩容，复制期间新旧缓存短暂共存。较长的自定义参考和其他生成预算不能套用短句峰值；原生层会拒绝超过上限的请求。当前固定参考声源的 65+360 预算不超过 512。

## A/B 结果

同一候选 DLL、同一组 8 条文本、分别启动独立进程，仅切换渐进缓存开关。Windows GPU Process Memory 每 100 ms 采样，报告语音进程在各适配器上的计数，另开 Vulkan 分配日志佐证；不是整张卡的占用。驱动 NVIDIA 581.08、AMD 32.0.11038.3，Ryzen 7 7735H、约 15.2 GiB RAM。

| 设备 / 计数 | 固定 1024 缓存 | 渐进 FP32 缓存 | 变化 |
|---|---:|---:|---:|
| RTX 4050 专用显存采样峰值 | 1212.738 MiB | 1044.914 MiB | -167.824 MiB，约 13.8% |
| RTX 4050 共享显存采样峰值 | 94.332 MiB | 94.332 MiB | 未转移到共享内存 |
| AMD 核显共享显存采样峰值 | 1201.566 MiB | 1030.738 MiB | -170.828 MiB |
| AMD 核显专用显存采样峰值 | 17.336 MiB | 40.809 MiB | +23.473 MiB，须同时保留 |

两种 GPU 各 8/8 条音频的 FP32 PCM SHA256 与本设备对照一致，包括长短句、数字、中英混合、生僻字和重复句。各设备输出不同，不能跨设备比较哈希。一次对照的时间受后台负载、文件及着色器缓存影响，不宣称稳定提速；最初一次旧 DLL 出现约 25 秒首次编译等待，不能与暖缓存的候选首次延迟直接比较。

独显仍会使用 RAM：Python、文件映射、文本处理、音频队列和驱动需要系统内存。这轮独显空闲实测物理驻留约 1 GiB，共享 GPU 内存约 94 MiB。进程私有提交包含不同于物理驻留的记账，不能把它与 RAM、GPU 专用及共享占用直接相加。

半精度 KV 实验也完成：峰值约 1044 MiB，但短句由 76800 变成 82560 个样本，长句长度与波形也变化。因此 **FP16 不进入采用方案**；正式补丁只有 FP32 渐进缓存。

## 启动条件

- 核显仍需启动前 3 GiB 系统可用内存，内存不足后恢复为 3.5 GiB。
- 渐进缓存、精简 Q8、文字词表按需加载同时启用，且实际识别为 NVIDIA 独显时，启动门槛降到 **2.75 GiB**，自动恢复 **3.25 GiB**。其他独显、未知设备、旧布局保留原门槛。
- 两轮在真实检查点分别剩余 2.7941 / 2.7850 GiB，成功加载并完成长短句，PCM 与对照相同；最低观测余量 2.0850 GiB，未触发测试的 1.5 GiB 安全中止。
- 2.5 GiB 候选未采用：虽加载成功，一轮测试在后续合成时降至 1.4998 GiB，测试释放自身占位页并报失败。失败记录保留，不通过删除失败样本来降低门槛。
- 以上是系统可用 RAM 条件，不是“模型峰值一定占这些内存”，也不是游戏并行或所有型号的保证。独显约 1.02 GiB 专用显存峰值不能直接换算为系统 RAM 门槛。

控制页把“当前可用系统内存”和“启动至少需要”并列，直接给出满足条件/还差多少、实际 GPU、语音物理驻留；提交内存与解释放入可保留展开状态的说明。运行状态显示实际 KV 容量和分配量，标明仅为缓存。

## 复现

先按 `scripts/build_native_windows.ps1` 编译固定版本，脚本依次应用已有补丁及 `evidence/2026-10-15-vram/qwentts-progressive-kv.patch`。不要对旧 DLL 只改配置。构建脚本已固定上游与 ggml 提交。

开发时在 CMake 构建目录启用 `-DQWEN_TEST_ADAPTIVE_KV=ON`，构建并运行 `test-adaptive-kv`；通过 `GGML_BACKEND=Vulkan0` 和 `GGML_VK_VISIBLE_DEVICES` 明确指定被测硬件。普通用户无需构建测试程序。

复制运行配置，在新的独立测试目录使用新 DLL 及其 SHA256，保留模型和音色特征的原哈希，设置 `adaptiveKv: true`。测试不同开关时用独立进程，不能在同一个 Vulkan 进程里反复改环境变量。

```powershell
$env:PYTHONPATH = (Join-Path (Get-Location) 'src')
python scripts/benchmark_vram.py --runtime <测试运行时目录> --device <Vulkan完整设备名> --output <测试结果目录>
python scripts/benchmark_loading_memory.py --runtime <测试运行时目录> --device-name <设备名> --target-free 2.8 --max-ballast-mib 6144 --cycles 2 --output <结果.json>
```

第二个命令仅用于开发验收：创建有上限的随机占位页，在加载前施压，系统可用内存低于 1.5 GiB 时只释放测试自己的缓冲并中止。正常运行不创建占位页，不清理其他程序。占位页包含在测试进程的内存统计中，不可当成模型占用。

完整数字、失败样本与补丁见 `evidence/2026-10-15-vram/`。未来项目：更多型号/驱动、游戏共存、原生图临时空间复用；尚未完成的方向不计为本次收益。
